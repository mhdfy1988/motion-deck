## 最重要的纠正：拖肘不是固定手的弯曲目标

`handlePointerDown`先取关节标记，再用`getChainForBone`查肢体链；命中`chainDef.poleBone`时设置`targetType='midJoint'`，根骨为链中其前一根骨。鼠标射线与经过被点关节的观察平面求交，保存点击偏移。按下时更新骨架矩阵与末端目标，避免拿到上一次姿态的位置（核心1853–1968）。

移动进入`midJoint`分支（2143–2173）：

1. 用平面交点加起始偏移得到目标位置。
2. 读取当前肘/膝世界位置。
3. `rotateBoneToPoint(rootBone, midWorld, targetPos)`转动上臂/大腿，不移动其局部位置，不直接求固定末端的IK。
4. 子骨骼随父骨旋转，手/脚自然跟着走；随后把IK末端目标同步到新的真实手/脚位置，避免下一次求解拉回旧位置。

旋转辅助函数650–702实际对齐的是方向：`当前方向=(子关节-根).normalize()`，`目标方向=(鼠标目标-根).normalize()`，用叉积轴和点积夹角生成世界增量，再换回父骨坐标系写局部四元数。它保持骨长，因此肘/膝落在以肩/髋为中心的球面，不保证严格贴到任意鼠标三维点；不要照抄注释“perfectly on mouse cursor”当成实际行为。

例：肩在(0,0,0)、肘(1,0,0)、手(2,0,0)，鼠标目标(1,1,0)，转45°后肘约(.707,.707,0)，手约(1.414,1.414,0)。这是算法说明，不是参考程序实测。

MotionDeck当前圆点拖肘却调用`LimbIK.movePole`，固定手与肩的位置、绕肩—手轴转弯曲平面；伸直时无自由度所以拒绝。这是另一种有用途的工具，不是参考默认拖肘的等价实现。参考的父骨转向不需要先弯肘，因此直臂也能抬落。此前把这两种操作混用，是最直接的偏差。

## 整套交互的对照

| 用户操作/规则 | 参考源码事实 | MotionDeck当前差异及纠正 |
| --- | --- | --- |
| 命中人体 | 先射线命中关节点；没中则命中蒙皮表面，找距离命中点最近的骨（1980–2072），再按该骨所属链分流 | BodyControls主要是覆盖在画面上的DOM点，没有等价人体表面选骨链；点变小不等于交互已等价 |
| “抓骨段”措辞 | 这里没有专门的射线到骨段距离拾取；视觉上拖中手臂，可能实际解析成最近的肘、腕或上臂 | 上一轮按视频直接称“骨段拾取”证据不足，需撤回。视频不能确定精确命中了哪根骨；需参考运行才能逐手势对应 |
| 拖肘/膝 | 转父骨，手脚随动，再同步末端目标（2143–2173） | 我们做成固定末端的弯曲方向工具，语义不同，不应取代普通抬臂/摆腿 |
| 拖手脚及其他链内骨 | 非midJoint走末端目标更新+两骨求解（2175–2181）；并不是所有骨都直接绕父骨转 | 不可把新认识再泛化成“抓任何骨段都会绕父关节转”；需按实际命中骨分流 |
| 手脚/腕朝向 | 普通两骨求解修改根与中间骨旋转（532–647），此链路没有把末端世界四元数恢复到起始值；手腕可另外旋转 | 我们主动保持手脚世界朝向，是额外产品策略，不是忠实复刻。把绝对掌向不变当普适自然行为，会造成手臂抬起而掌向抵消；具体效果需真实姿势检查 |
| 拖肘与显式弯曲目标 | `midJoint`不走`solveIKForPoleTarget`；后者另在2618起读末端和弯曲目标重解 | 应把“整臂摆向”和“固定末端调弯曲面”作为两个意图分别理解，而非同名替代 |
| 选中/悬停反馈 | `updateMarkers`把相关链各骨及末端纳入高亮，选中优先于悬停，尺度/绘制顺序也区分（2912–2980） | 我们主要高亮单个按钮；没有完整表达此次影响整条链 |
| 点击和拖动收尾 | 拖动后清理选择/旋转环，不拖动则选骨附着旋转环（2232–2279） | 我们`finishPointer`拖后也choose，立即挂旋转环；这不是参考默认行为，可能增加视觉干扰 |
| 握手操作 | freepose1354–1378接角度滑杆、左右手预设和OPEN到FIST握紧插值；一组手指共同变化 | 我们尚未接入指握控件，仅有逐骨精调；“能逐根手指旋转”不能当成“用户能方便握剑” |
| 外层配置 | freepose107明确`useHandControlPopover:false`；默认核心可隐藏指骨并触发掌面弹层，但该页关闭它 | 不能把核心里存在的手掌弹层说成视频页面已启用的功能 |
| 观察和输出镜头 | freepose1069–1118区分摆姿/定镜头；1223–1287重配鼠标及捕获优先级；198起`snap`决定是否同步观察到输出镜头 | 我们主要是一台编辑/预览相机加自由观看，不能把预设视角或右键飞行当作相同镜头工作流。此处仅核对与摆姿有关的边界，非完整相机专题完成 |

## 需要保留但不能冒充原版的决定

MotionDeck骨长/缩放保护、跨模型限制、统一草稿事务、失败回滚以及取消/失焦保护是本项目的正确边界；默认只读也是产品规则。它们并不证明摆姿交互已经等价。固定手脚世界朝向、固定末端拖肘属于可选择的额外策略，不应无说明地取代参考默认动作。参考自身也没有因此具备完整人体限位或自动防穿模。

## 为什么此前“测试全过”仍没达到用户目标

之前测试验证“固定末端不动”“四元数不变”“一步撤销”等实现自定不变式，没有验证参考语义“抓肘直臂可抬起、手跟着走”。数学正确只能证明选定的工具正确，不能证明选对了工具。后续若实现，验收样例必须先从参考真实操作取：点/表面怎么命中、拖哪个部位、哪些部位应移动/保持、旋转环何时出现、握持与观察如何配合，再确定数值约束。

本轮到此只确认静态源码差异。尚未逐手势运行参考、未比较同一姿势的实机画面、未完成自然度验收，不宣称“全部学完/已复刻”。

## 头、胸、腰与手脚是否统一（追加源码核对）

- 不是统一“拖哪一关节就只转它的上一根骨”。`IK_CHAINS`核心241–246明确有躯干链：`spine_01 → spine_02 → spine_03 → neck_01`，末端目标`head`，没有`poleBone`。默认`ikEnabled:true`（1080），控制器各链默认ik（903–906），2790起为现有末端骨创建目标；不能只看定义就说用户入口已接，也不能漏掉初始化/模式判断。
- `handlePointerDown`1907起通过`getChainForBone`953起把腰/胸/颈/头归到躯干链；只有`poleBone`命中才走midJoint。躯干无该字段，因此走effector。平面基于被点骨深度，但offset是头部目标减射线交点（1935–1950）；拖胸/腰实际移动的是头部目标的增量，不是把头直接吸到胸前鼠标位置。2143–2181、2493起接入求解，四骨链在715–814走CCD，多根脊柱旋转；躯干祖先转动时头/肩/手臂等下游随层级变化，不是只动头或单根胸骨。
- 手/脚也走effector，按两骨解（715–746），可能同时改变上臂与小臂／大腿与小腿。用户新提出的“肘膝固定、只转小臂/小腿、手脚局部姿态不变”是MotionDeck拟采用的逐段操作规则，不是参考默认手脚拖动。此前口头说“统一同一套规则”只应解释需求，不得据此反推参考实现。
- 肘/膝的midJoint分支才是只转上臂/大腿、下游随动。骨盆另有isRoot分支（201–207、2512–2598），移动骨盆后重解双腿，尝试保留原脚位置；不等于所有后代毫无约束地整体平移。
- 点击未拖时可通过selectBone2303–2318直接选择该骨挂局部旋转环，这与上述直接拖动的多关节求解必须分开讲。以上为固定快照静态调用链结论，未运行参考程序验证人体自然度。
